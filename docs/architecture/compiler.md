The [playground](/play/) builds a program and runs it without anything installed, and so does [`yaroze`](../tools/yaroze.md). The compiler behind both is TinyGo itself, compiled to WebAssembly, with LLVM and lld linked into it the way a release build of TinyGo links them. In the browser it runs against a file system held in memory, and on the desktop `yaroze` runs it in-process under [wazero](https://wazero.io/). [`web/compiler`](../../web/compiler) holds the recipe, and `build.sh` is the whole of it.

## TinyGo compiles TinyGo

TinyGo is a Go program bound to LLVM through cgo, and Go's own WebAssembly ports have no cgo. TinyGo's does: its wasip1 target compiles the C parts with clang and links them with wasm-ld. So TinyGo compiles TinyGo, against LLVM built for wasm32-wasi:

- **LLVM** (`llvm/configure.sh`): LLVM, clang and lld as static libraries for wasm32-wasi, with only the Mips backend, no threads and no tools, using nixpkgs' wasi cross toolchain. `llvm-wasi.patch` and `wasi-compat/` are what LLVM's Support library needs to compile without signals, processes, sockets or users: a few declarations and stubs, and the code paths that catch crashes or run subprocesses cut out. The patch also holds the changes to the Mips backend that [Code for the R3000](#code-for-the-r3000) describes. `libcxx.sh` builds libc++ with its threading API on, because LLVM's headers use `std::mutex` whatever `LLVM_ENABLE_THREADS` says. Nothing ever starts a thread. It builds from the patched tree, since libc++ 23 needs one line of the patch to build against wasi-libc, and clang's constant interpreter another, which keeps it off tail calls that WebAssembly has only as an optional feature.
- **Glue** (`glue/`): the C and C++ that is not LLVM's. That is go-llvm's bindings, an lld driver with only the ELF linker, TinyGo's clang driver for the full build, and `wasi-stubs.c`, the POSIX functions LLVM links against and WASI does not have, each failing the way a system without the feature would, and an `sbrk` that gives wasi-libc's allocator pieces of TinyGo's heap. C's memory is that allocator's (the `custommalloc` tag), since LLVM makes millions of small allocations per build and TinyGo's allocator is slow at that; the pieces are manual allocations the collector neither scans nor frees, so the Go side is collected as before, and the runtime's heap starts past the initial memory the allocator takes for itself first (`tinygo_morecore` and `heapStartAddr` in the runtime). dlmalloc assumes `sbrk` is contiguous until a call fails, so the first is refused.
- **The target** (`target/gen.sh`): wasip1, with every library above on the link line and a 32MB stack, since LLVM's recursion needs far more than the usual 64K. With less, it overflows and corrupts memory, and fails differently on every build. The compiler is built with no scheduler (`-scheduler=none`, and `-panic-unwind=explicit` so that recover works without asyncify): the patch has the builder run its jobs one after another rather than each on a goroutine, and go/ssa build packages in turn, and gives `os/exec` and the parking in `internal/poll` shapes that start nothing. With the asyncify scheduler every goroutine got a 32MB stack and switching unwound the whole stack, which was most of a build's time, and asyncify's instrumentation was a third of the module. DWARF is left out of the IR too, since nothing in the playground reads it; `-debug` keeps it.
- **TinyGo** (`tinygo-wasm.patch`, applied by `prepare.sh` to upstream TinyGo at the flake's revision with the `playstation` target from `internal/toolchain/_tinygo` laid over it): those files are only additions, as a pull request to TinyGo would be, and the patch holds what running the compiler as a WebAssembly program needs. That is `cmd/tinygo-wasm`, the build command alone, and under the `wasm` build tag a loader that lists packages with go/build instead of running `go list`, takes GOROOT and GOVERSION from the environment instead of `go env`, uses a GOROOT merged in advance, and runs lld in-process instead of as a subprocess. Two more parts are about the version rather than WebAssembly. TinyGo 0.44 compiles the C++ files of a cgo package itself, and here those are the glue above, so the patch adds an `extcxx` build tag that leaves them to the glue step. And TinyGo's own static builds are still of LLVM 22, so its copy of clang's assembler driver (`builder/cc1as.cpp`) is brought to LLVM 23's interfaces, as clang's own `cc1as_main.cpp` has them. `cmd/tinygo-sysroot`, also in the patch, gathers that merged GOROOT, the psx packages and the target files into the tree the compiler reads. `prepare.sh` says how to regenerate the patch.

## Leaving clang out

A release TinyGo compiles a target's C and assembly with an in-process clang, and clang is more than half of the module. So there are two builds. The shipped `tinygo.wasm` leaves clang out and is 44MB, 14.5MB gzipped. `tinygo-full.wasm` keeps it, at 107MB, and never leaves the build machine: `mkcache.sh` runs it under wasmtime over every example, against the same sysroot paths the browser uses, and the cache it fills ships in `sysroot.tar.gz`, keyed by the shipped compiler's hash. A first build then finds the target's C and the standard library already compiled. The playground's sysroot holds the cache at TinyGo's default `-opt=z` and is 5MB; `yaroze`'s holds `-opt=2` as well and is 8.4MB, without the bitcode of each program's packages linked into one module, which the cache can also hold, as a first build measured no faster with it.

`tinygo-full.wasm` also takes `clang` and `ld.lld` as its first argument, to run those tools alone, and that is how `yaroze` builds a [C project](../tools/yaroze.md#c-projects). It downloads the module the first time, 30.5MB gzipped, from where `cmd/yaroze/wasm/full.json` says, so only those who build C pay for it.

## A build in the playground

`compile-worker.js` fetches the compiler, the tools and the sysroot once. The compiler comes from R2, gzipped, where `play/compiler.json` says, which the site's build writes (`web/compiler/site-compiler.sh`): the release of the compiler `yaroze` embeds, which the build checks is that compiler byte for byte, since the site's discs are built by it, so the site serves no 44MB module of its own and a page always loads the compiler it was built with. A compiler `task compiler` built, which need not be on R2 yet, is served beside the page instead. The bucket's CORS rule lets the site's origins read it: the GitHub Pages site, the Cloudflare Pages previews and `task serve` on localhost. `pipeline.js` runs each build in a worker: the program's `//go:generate` lines, then the compiler, then `mips1fix`, `eco2exe` and `mkdisc`. The tools are the repository's own, compiled to wasip1 by the Go toolchain and run through `wasi.js`, a WASI host over an in-memory file system. The result is a disc the player boots like an example. The packages a program imports are linked into one bitcode module the first time that set is seen and kept in the cache (`prelink-*.bc`, keyed by the packages' own cache entries), since a build changes the main package alone nearly always and parsing one module is quicker than parsing and linking thirty; the cache the sysroot ships holds the examples' sets. The compiler is loaded once and asked to build as often as needed (`Compiler` in `pipeline.js`): the module is a reactor, with `tinygo_args` and `tinygo_build` exports in place of a command line, and between builds its loader keeps the standard library and the imported packages parsed and type-checked, in one file set and one SSA program (`loader.Keep`, `loader/keep.go`), since a build changes the main package alone nearly always. A build of the square example takes about 0.3s on a desktop after the first in a page, which takes about a second while the browser compiles the module's code as it runs and the compiler reads the standard library. So once the compiler has loaded, which the editor's first use starts, the page builds the project as it stands in the background, and again a little after each change to it while the page is in view; when the program is the same by the time Run is pressed, that build is used and Run is immediate (`prebuild` and `schedulePrebuild` in `playground.js`).

What is built is a project (`project.js`): the program's Go files, a tab each over the editor in the Code layout (`files.js`; the page's three layouts are `layout.js`), and its data files, in the sidebar's tree (`sidebar.js`) and shown in the Assets layout (`inspect.js`, with `sprite.js` to draw a picture), uploaded or copied from an example. The data goes under `assets/`, for `mkdisc` to put on the disc where the program registers it with package `disc`. Sources under `assets/` are converted by the program's own `//go:generate` lines (`convert.js`), which the worker runs with the converters built to wasip1. A scene is placed in the Scenes layout (`scene-tab.js`, drawing with `preview.js`), its tile layers painted on their maps and their cells flagged, or painted as a room of cells for package `stage` (`room-edit.js`, which draws the room as the console does, through a camera with the game's eight angles), and cooked by `mkscene` the same way, for package `scene` to read on the console. Projects are kept in the browser's IndexedDB, and go out and come in as zips laid out like the examples, so a download runs with `go run`.

While a project runs, each cooked scene is also written into the emulator's RAM over the file the program loaded, and package `scene`'s `live` variable tells the program to read it again, so the console follows the editor without a rebuild. That goes through the worker's `symbol`, `peek` and `poke` messages to `psx.symbol`, `psx.read` and `psx.write` in `web/main.go`. The worker's `break`, `unbreak`, `step` and `registers` messages set breakpoints on the program's functions by the same symbols, pause it at one with a `break` event, and step it an instruction at a time.

## The target

TinyGo is given one target here, `playstation`, in `internal/toolchain/_tinygo`: the R3000A (`r3000.json`), a start-up, a link script and a little C (`playstation.S`, `playstation.ld`, `playstation-libc.c`), and a runtime (`src/runtime/runtime_playstation.go`). It knows nothing of the Net Yaroze. A program built for it alone owns the console, with only the BIOS underneath, and prints, keeps time and masks interrupts by itself. It is meant to go upstream as it is.

The runtime reaches the machine through six functions, the platform hooks, which the runtime's file documents: `psx_init`, `psx_putchar`, `psx_nanotime`, `psx_sleep`, `psx_disable_interrupts` and `psx_restore_interrupts`. The target's files define each of them weak, along with the start-up and the C library functions, so a target file that inherits `playstation` and lists a file with its own definitions replaces them, and no file of TinyGo's changes.

That is how a Net Yaroze program is built. Its files are in `internal/toolchain/yaroze`, which is not part of TinyGo's tree: the start-up, the link script (`yaroze.ld`), the resident library's addresses (`symusr.S`), the clean library's assembly (`clean.S`) and `runtime.c`, which answers the hooks with the library's `putchar`, `VSync`, `InitHeap` and critical sections. `yaroze` lays them over `playstation` with a target file for each way of building (`internal/toolchain/target.go`):

- **static**, the default, links the clean library, `internal/libps`, into the program, which loads at 0x80010000.
- **resident** (`--libps resident`) lays the program over the resident library's image, at 0x80090000, as original executables and a real Net Yaroze have it.
- **fidelity** is static with Sony's timing kept, for comparing with a reference (`internal/libps/build.sh`).

The target files are written into the sysroot, in `tinygo/yaroze` beside the files they name, when the sysroot is made (`go run ./internal/toolchain/mktargets`), so that `yaroze`, the playground and the scripts that fill the cache all build for the same ones, such as `/sysroot/tinygo/yaroze/static.json`. Each sets the `yaroze` build tag, its flags and the link script, and inherits a file of its own, `first.json`, ahead of `playstation`: TinyGo links a target's files in the order its target files name them, and the Net Yaroze's start-up has to be first, and the resident library's weak entry points have to come before the weak C library of the base target for the linker to choose them. A program's own target file (`--target`) inherits `playstation` too, and `yaroze` puts the resident build's target file in its place.

The hooks in `runtime.c` cost nothing. C and Go are optimized together at link time, and each hook is inlined into its callers, so a program has the same instructions as when the runtime called the library by name. Two things in the target keep that true: `r3000.json` gives the processor's features in the order clang writes them, since LLVM only inlines between functions whose features are the same text, and the C library functions are kept from being taken for builtins by a pragma in their file and not by a flag of the target, since a function compiled with `-fno-builtin` is never inlined into one that was not.

Since the compiler's key (`key.sh`) covers `_tinygo` and not `internal/toolchain/yaroze`, an edit to the library's assembly needs `task yaroze`, which compiles it into the cache, and no new compiler.

## Allocations made once

Nothing allocated on the PlayStation is ever freed, since the target uses TinyGo's leaking collector, so an object allocated at most once might as well be a variable. A pass added to TinyGo (`transform/once.go` in `internal/toolchain/_tinygo`, hooked in by `internal/toolchain/tinygo-once.patch`) gives each such allocation a zeroed global of its own, in `.bss`, where the linker places it and counts it against the program's memory, rather than taking it from the heap at run time. A program can then keep what its frame loop works on as locals in `main`: the closure the loop body captures them in makes them escape, but they are allocated once, before the loop, and come out laid out as package-level variables would. An allocation counts as made once if it has a constant size, is outside every loop, and is in `main.main` or in a function whose only use is a call from such a place, as a setup helper's is. It runs after TinyGo's own pass that moves allocations that do not escape onto the stack, which keeps them. Each global is named by its function, its size and the allocation's position, as `main.main$once.64@main.go:12:9`, for a `-hot` build: a patch binds its variables to the running program's by name and refuses one whose size changed, so an edit elsewhere leaves the names as they were, and an allocation that changed becomes a new variable rather than an error. A patch never runs `main` or its setup helpers again, so the new variable goes unused. In a `-hot` build the pass looks through each stub to the `F$body` it calls. `-print-allocs` lists what it moved, with the global's name. A variable made inside the frame loop and passed to the library needs none of this: TinyGo takes every `//export` declaration, the library's bindings among them, to keep none of the pointers it is given, cgo's rule, so the variable stays on the stack.

## What the library keeps

TinyGo takes every `//export` declaration, the library's bindings among them, to keep none of the pointers it is given, cgo's rule, so a variable whose address is passed to one stays on the stack. Sony's library breaks the rule in a few places: `GsSetWorkBase` builds packets where it was told to until it is told otherwise, `GsInitCoordinate2` links the two systems it is given to each other, `SsSeqOpen` reads the sequence for as long as it plays, and `LoadImage` goes on reading the pixels after it returns, until `DrawSync`. `yaroze/keeps.txt` lists them, from the clean room library's reading of Sony's, and `hdr2go --keeps` writes each onto its binding as a `//go:keeps` pragma: the parameter, and the function after which it is no longer kept, if any. `internal/toolchain/tinygo-keeps.patch` teaches TinyGo the pragma: such a parameter is marked with a `tinygo-keeps` attribute, and one kept for good is left able to escape, so that what is passed to it is allocated on the heap, or made a global by the pass above if it is allocated once. A pass after that one (`transform/keeps.go`) refuses what would still go wrong: a variable on the stack passed to a parameter kept until a later call, when its function can return before making the call, outside `main`; and one allocated each time a loop goes round, or each time a function runs that may run every frame, which is one called from a loop, a function value such as the frame loop's body, or one such a function calls, passed to a parameter kept for good. It follows the pointer back through address arithmetic, conversions, phis and the calls that return their argument, and from a parameter to each call of its function, so that a variable passed through a wrapper such as `RECT.Load` is found where it is made, and reported at the call in its own function, the program's line; a pointer loaded from memory is not followed. The compiler leaves DWARF out on the PlayStation targets, so the patch gives each call in a package outside the standard library its position as `tinygo.pos` metadata, which the pass reports; metadata, unlike an attribute, leaves the optimizer free to merge calls, so the code is the same as without it.

`yaroze vet` (`internal/keepcheck`) checks the same in the source, where it can name the variable, and `yaroze build`, `disc`, `run` and `patch` run it on the package before they compile it. Its table is generated from the yaroze package: the pragmas, and the package's own functions and methods that pass a parameter on to one, such as `RECT.Load`, which keep it too. It reads the syntax alone, so it follows a variable's address only through `&`, fields, elements, slicing and conversions, and takes a function literal or the body of a range over an iterator, such as `Screen.Frames`, as running every frame.

## Allocation in the frame loop

An allocation the frame loop makes each time round is never freed, and runs the program out of memory after minutes of play rather than at once. A pass in `internal/toolchain/tinygo-frame.patch` (`transform/frame.go`) refuses it at the build. The frame loop is a loop that waits for the screen, one with a call that leads to the library's `VSync`: `Screen.Frames`, in package `yaroze`, or the program's own loop in package `main`. A loop in another package that waits, as `disc.Wait` does for a read, is a wait and not a frame loop. What runs there is the loop's blocks, the functions they call, directly or through a function value of the type called, such as the body of a range over `Frames`, and what those call. The pass runs after the optimizer, so an allocation that went to the stack or was folded away is not counted. One reached only through a test the guarded code turns off, as a lazy allocation is (`if f.dst == nil { f.dst = make(...) }`, or a flag the code sets), is made once and allowed. So is what a panic allocates: the runtime may allocate to print a panic's value, the message of an error for one, and then it stops the program, so what the runtime's functions that do not return allocate does not count for their callers. What the program's own code allocates for the value it panics with is reported as any other allocation.

It reports the program's line: the allocation in its own code, the call into the standard library that allocates, such as `strconv.Itoa`, a string concatenation or an `append` that grows, and for an allocation in another package, the call in package `main` that leads to it. Each call carries its position in `tinygo.pos` metadata, as for the keeps pass, now every call `createCall` makes, with the instruction's position and the package it is in, so that code inlined from another package is still told apart. The standard library's packages are those the loader finds in GOROOT, TinyGo's own among them, and every other package is the program's, whatever its module is named: the builder lists them for the passes (`Config.ProgramPackages`), so `play/level`, in the playground's module `play`, is the program's code and gets positions like any other. A function marked `//go:allocates` allocates on purpose, as a level load does, and the frame loop may call it: neither the call nor what the function allocates is reported. The pragma also keeps the function out of line, so that what it allocates is still found inside it once the optimizer is done. `scene.NewArchive`, `scene.Archive.Lookup`, which unpacks an entry the first time and keeps it, and `archive.Entry.Load` have it, and a program's own loader can too. `scene.Scene.Load` allocates nothing, so it needs none: it looks paths up in a buffer of the scene's own, and `LoadFiles` keeps the disc's files in the scene, where `scene.Files(files)` would allocate a `Source` for each load. A function marked so does not count as allocating for its callers either, so an interface call that may reach one is not reported for it.

The patch also fixes the leak that the check found most often. `go/ssa` loads the value a range ranges over even when only the index is used, `for i := range arr`, and TinyGo copied an aggregate that large into storage of its own, on the heap: 24KB each time for an array of 256 structs. A load nothing uses is no longer made.

A second pass (`transform/callback.go`) checks the functions the library calls from an interrupt. `VSyncCallback` installs a C function, and `yaroze.OnVSync` installs one that calls the Go func it is given: a top-level function of the package, whose address alone is enough to call it, since a function that is not a closure ignores the context a C caller does not pass. Interrupts are off while it runs, so the pass refuses an allocation in it, or a call of `VSync`, `DrawSync`, `CdSync` or `CdReadSync` that waits, in the function or what it calls. It finds the functions from the address passed to `VSyncCallback`, through a call of a func value to each function stored where the value is loaded from, and through a parameter to what each call passes.

## Hot reload

A program built with `-hot` (`yaroze run --hot`, or the playground's Hot box) can be given new code while it runs. The compiler, in a pass added to TinyGo (`transform/hot.go` in `internal/toolchain/_tinygo`, with the flags and hooks in `internal/toolchain/tinygo-hot.patch`), renames each function of the main package `F` to `F$body`, keeps it out of line, and puts a stub `F` in its place that loads `F$slot`, a word holding the body's address, and tail-calls it. Every call, function value and method table goes through the slot, so writing the slot changes what runs next, including the frame loop's body, which `Screen.Frames` calls through its function value every frame. The load is volatile, so the optimizer keeps it. The optimizer is also kept from narrowing or folding away the variables of the program's own packages, which are those outside GOROOT, by a function that is never called and loads each of them (`__hot_keep`), so that a patch finds every one at the size the running program has. The variables of the runtime and the standard library are left to the optimizer. The link script reserves 256KB above the program for patches, and the Go heap starts above that; a program so large that this would leave the heap under 256KB gets a smaller region, down to none, which `yaroze run --hot` and the playground say.

A patch is the same program compiled again with `-hot-base`, the ELF of the running program, and `-hot-at`, an address in its region. After the optimizer, a second pass binds the module to the base: every function the base has becomes its address there, every writable variable too, since that is the running program's state, and every type descriptor, since interfaces compare types by address. Read-only data is compiled afresh, so a changed table or string is the new one. The bodies are kept and linked at the address, with `__hot_patch`, a table of the base's slots to point at them, and anything the base lacks, a new function or variable, is compiled in with it. A constant is folded into the code that uses it, so a changed constant is in the new functions; a variable set from one keeps its value, since it is the running program's state, except that `__hot_inits` carries the old and new initial bytes of every bound variable whose initial value changed, and the loader gives the new value to a variable that still holds the old one, which the program has not written since it started. The `hot` package (`internal/hot`) reads the patch's sections and table, and loads it the next time the program calls the library's `VSync`, where every frame of the main package's code has returned: `yaroze run` through its window, and the playground through the worker's `patch` message to `psx.patch`. Each patch is linked after the one before, since the program may still be running that one's code, until the region is full.

What a patch cannot do, the compiler reports as an error starting `hot:`, and the program has to be built and started again: a variable that changed size, a function and a variable swapping names, and a function literal written in `main`, such as the frame loop's body, that captures other variables than before. `main` made that one value when the program started and goes on calling it, so the new body would read the old captures wrong; the base records how each such literal unpacks its context, as a variable `F$captures`, and the patch compares. A literal in any other function is made again by that function's new code, and may change. A patch built with other [experiments](#experiments) than the program is refused too, since a patch holds the main package's code alone and the library's stays the program's: a program built with `onstore` has drawing code that does not pack, so a patch built without it would leave its sprites' words stale. The link of a `-hot` program defines an absolute symbol for each experiment, `__hot_experiment_onstore`, 1 if it is on and 0 if off, which takes no memory, and the patch compares its own settings with them. A program with no such symbol, built by an older compiler, is refused as well, since nothing says how its library was compiled. What it cannot see is the user's: a type whose layout changed while objects of the old layout are live, or a running function, `main` itself, whose old activation goes on in the old code until it returns. Those are the ways a patched game misbehaves, so the feature is opt-in. The cost of the slots is a load and an indirect jump at each call into the main package, which at the size optimization is the calls the compiler would otherwise have inlined.

## Experiments

An experiment is a change to how the compiler builds a program that is on by default and can be turned off, as Go's `GOEXPERIMENT` turns changes in progress on and off. `yaroze build`, `run`, `disc` and `patch` take `--experiment=NAMES`, a comma separated list with `no` before a name to turn it off, and pass it to the compiler's `-experiment` flag. An experiment may be removed, changed, or folded into a better optimization, so nothing should depend on one being there: a program built with all of them off is always correct. The playground builds with them on, as they are by default, and its Onstore box, unticked, builds with `noonstore`. There is one, `onstore`.

### onstore

Some of the structs the library reads keep a word laid out for it that is worked out from Go fields. A `yaroze.Sprite` begins with the SDK's `GsSPRITE`, whose attribute word holds the sprite's `Blend`, its texture's color depth and `Unlit`, and `Box`, `Line`, `GradientLine` and `Background` hold the same word for their blend. Packing the word each time a sprite was drawn cost 24 cycles of the 254 a plain `Draw` takes. The fields change far less often than a sprite is drawn, so the onstore experiment keeps the word up to date as they are set instead.

A method marked `//go:onstore` with the names of fields of its receiver's struct, as `//go:onstore Blend Unlit Texture` on `func (sp *Sprite) pack()`, is called after every store to one of those fields, or to something inside one, such as `Texture.Page`, wherever in the program the store is: `sp.Blend = yaroze.BlendAdd`, `sprites[i].Unlit = true`, or `e.Sprite.Texture = tex` through a struct the sprite is in. TinyGo's frontend, which turns go/ssa into LLVM IR, adds the call after each such store, on the object the field is in (`compiler/onstore.go` in `internal/toolchain/_tinygo`, hooked in by `internal/toolchain/tinygo-onstore.patch`), and makes a single call after the last of consecutive stores to the same object. The method is always inlined, so a call costs its few instructions. A package-level variable set by a literal, as `var ship = yaroze.Sprite{Blend: yaroze.BlendAdd}`, gets its word at compile time, since TinyGo runs package initialization in the compiler where it can. Copying a whole struct needs no call, since the word is copied with it, and reading a field calls nothing. With the experiment on, the compiler builds with the tag `psx.onstore`, and package `yaroze` packs the word when drawing only in a file built without it.

The compiler sees only the stores it makes itself, so the word goes wrong after:

- a write through `unsafe` or `reflect`, such as a pointer to the struct converted to another type;
- a struct filled from bytes, as decoding it from a file into its memory does, or one the library or a DMA transfer writes;
- a store through a pointer to a watched field. The compiler refuses to build a program that uses such a field's address for anything but a store or a load, as passing `&sp.Blend` on, keeping it, or calling a method with a pointer receiver on `sp.Texture` does, and names the position.

Only packages under `go.chrisrx.dev/psx` may use `//go:onstore` while it is an experiment, so that changing or removing it touches no program's code. If a program draws wrong and the experiment may be why, `--experiment=noonstore` builds it as before: no calls are added, the tag is left out, and drawing packs the word each time.

## Code for the R3000

The PlayStation's processor is a MIPS I: the instruction after a branch runs whether or not the branch is taken (the delay slot), the instruction after a load still sees the register's old value (the load delay), and there is no branch prediction, so a conditional branch costs the same taken or not. LLVM's Mips backend is written for later processors, which have neither the load delay nor that cost, and the rest of `llvm-wasi.patch` is what it takes to make its code right and short on this one. All of it applies to MIPS I alone, and the changes to the delay slot filler are in `llvm/lib/Target/Mips/MipsDelaySlotFiller.cpp`.

**Loads in delay slots.** A load in a branch's delay slot is checked against the first instruction at the branch's target and on its fall-through, which must not read the register (`delayExposesHazard`). LLVM checked the first instruction in the block, which may be a debug value that emits nothing, and went on to move that first instruction away into a later slot. The patch checks the first instruction that runs (`firstExecutedInstr`), and refuses a move that would leave a load already in a slot in front of an instruction that reads it (`moveExposesLoadHazard`). `tests/loaddelay_test.go` scans every built program for a load whose result the next instruction reads.

**Block placement.** LLVM lays a loop out to have as few taken branches as it can, and for that it moves a loop's last block, the one that counts and branches back, above the loop's first block when the loop's body has more than one way to reach it. Each of those ways but one then needs an unconditional jump, which is two instructions on this processor, with its delay slot, where the taken branch it saved cost nothing. `TargetSubtargetInfo::isTakenBranchFree` says that a taken conditional branch is free, the Mips subtarget answers yes for MIPS I, and `MachineBlockPlacement` then leaves such a block at the bottom of its loop. A block with one successor, which ends in an unconditional jump wherever it is, is still moved.

**Slots filled from a successor.** The filler looks backward from a branch for an instruction to put in its slot, and it can look in the blocks the branch leads to as well, but LLVM leaves that search off. The patch turns it on for MIPS I (`-disable-mips-df-succbb-search` still turns it off), where a load ahead of a branch that tests what it loaded is common and leaves the backward search nothing to take. It also tries each successor in turn rather than only the likeliest. An instruction taken from one successor runs on the way to the others too, so it has to be safe there: it may only touch general purpose registers, none of which another successor reads before writing; it may not store, trap or have any other effect; and it may load only what is safe to read early, below. The patch also fixes the search letting a load from the stack move above a store to the same slot.

**The load delay ahead of a branch.** When a conditional branch reads what the instruction before it loaded, a nop has to go between them (`MipsBranchExpansion` adds it). `fillLoadDelay` looks for an instruction to put there instead, in a successor that only this block leads to, under the same rules as for a slot, and with the further rule that the instruction does not depend on the branch or on what is in its slot, since it moves ahead of both. `-disable-mips-df-load-delay-fill` turns it off. The filler also no longer takes an instruction for a slot when that instruction is all that separates a load from its use, which only moved the nop.

**Which loads may run early.** A load that runs on a path that never asked for it is a danger on this machine: reading a hardware register can change what the hardware does next, an address with nothing behind it or a misaligned one stops the processor, and the branch the load moves above may be the test that guards it, a nil check for one. So the only loads moved onto another path are loads from the stack, loads of constants, and loads that LLVM marks dereferenceable from a global variable the program itself defines, none of them volatile, and none moved above a store. A global the program defines is memory the linker lays out, there on every path. A load through a pointer argument or a loaded pointer is never moved, however sure its own block is of the pointer, and neither is a load from a variable that is only declared, whose address a linker script could give to anything. Nor is an array's element at an index that is not a constant, which LLVM does not mark dereferenceable. `TestGuardedLoadsStay` builds a program with a bounds test and a nil test and checks that the loads behind them stay there.

**Backports.** Two hunks are LLVM's own, from after the 23.1 release, taken as upstream wrote them so that a move to an LLVM that has them deletes them from the patch:

- `71db60ced7`: the check of a delay slot's candidate as `delayExposesHazard`, shared by loads on MIPS I and by moves out of the floating point unit on MIPS I to III, and `lwc1` counted as a load with a delay. Our `firstExecutedInstr` changes sit inside that function, and `moveExposesLoadHazard` covers the floating point moves as well.
- `73641283fc`: MIPS I is no longer called experimental, in the features' descriptions or in a warning on every build.

Neither changes the code of the examples: the PlayStation has no floating point unit. A third, `a97f512d71`, by which `getInstSizeInBytes` counts an instruction's delay slot, was in the patch for LLVM 22 and is part of LLVM 23.

Together these take a loop that tests a field and calls a function, as drawing an array of sprites that may be hidden does, from 13 instructions an iteration to 9, and the code of the examples comes out 2 to 4% smaller. Readouts of time in five of the emulator tests' screenshots went down by one with it. To work on the patch, build a native `llc` from the patched tree under `.build/compiler/llvm-src` with only the Mips target, give it the bitcode the native TinyGo writes with `-o prog.bc`, and compare the assembly. That takes seconds, where the compiler takes half an hour.

## Building it

`task compiler` builds the two modules, which takes most of an hour, and `task playground` adds them, the tools, gofmt and the sysroot to the site. The fork is checked out at the revision `flake.nix` pins, so the compiler in the browser is the TinyGo the examples were built with, and `task yaroze` copies the same compiler and a sysroot into `cmd/yaroze/wasm` for `yaroze` to embed.

The Pages workflow deploys a pull request from this repository to Cloudflare Pages, as `pr-N.psxsdk.pages.dev`, and comments with the link, since GitHub Pages has the one site. A pull request that changes the compiler carries the refreshed embedded files, so its compiler has to be on R2 before it is pushed, from `task compiler:release`, which the build checks.

In CI, the Compiler workflow builds the modules when `web/compiler`, the flake, the PlayStation files in `internal/toolchain/_tinygo` or the patches beside it change, or on request. It caches them under a key made of those, less the Markdown (`key.sh`), and publishes them to the `psxsdk` bucket on Cloudflare R2 under that key (`release.sh`), served from `files.yaroze.dev`, which outlives the cache's week. A compiler published from a local build (`task compiler:release`) before the change is pushed saves the workflow the build, which is the usual way, and it writes `cmd/yaroze/wasm/full.json` for `yaroze` to embed. The workflow only needs the bucket's credentials as secrets if it does have to build. Cloudflare keeps a 404 for hours, so the scripts ask whether a compiler is there with a query string of their own, never the file's own URL before it is uploaded.

## Limits

- The shipped compiler has no clang, so a Go program cannot use cgo or anything whose C is not already in the cache. Only the ELF flavor of lld is linked in, for size.
- The cache and the sysroot are made together, by `task playground`, and a compiler with another hash ignores the cache.
- The compiler builds only at the optimization levels its cache holds, and only the ways of building whose C and assembly it holds, which `env.json` lists: static and, since the cache is filled over a program built that way too, resident.
- Memory is TinyGo's garbage collector's, LLVM's allocations included, and is scanned conservatively.
- A project is kept in the browser that made it, until it is downloaded.
